# Tray-клиент на Ubuntu 24.04

Tray-клиент запускается файлом `client/status_tray.py` и работает с ESP32 по локальной сети. Облачный сервис и MQTT-брокер не нужны.

Проверка приложения на Ubuntu 24.04 ещё не выполнялась. Команды ниже описывают целевую конфигурацию; значок в системном лотке, автозапуск и работу с реальным ESP32 необходимо проверить на Ubuntu.

## Зависимости

Нужны системные пакеты Python 3, PyGObject, GTK3 и AyatanaAppIndicator3:

```sh
sudo apt update
sudo apt install python3 python3-gi gir1.2-gtk-3.0 gir1.2-ayatanaappindicator3-0.1
```

Python-зависимости через `pip` не требуются. Автозапуск использует `/usr/bin/python3`, чтобы видеть модули, установленные через `apt`; активный virtualenv для него не нужен.

Проверить доступность GTK и AppIndicator можно отдельно:

```sh
/usr/bin/python3 - <<'PY'
import gi

gi.require_version("Gtk", "3.0")
gi.require_version("AyatanaAppIndicator3", "0.1")
from gi.repository import AyatanaAppIndicator3, Gtk

print("GTK3 и AyatanaAppIndicator3 доступны")
PY
```

## Установка автозапуска

Из корня репозитория выполните от обычного пользователя, без `sudo`:

```sh
bash client/install_ubuntu.sh
```

Скрипт проверяет Ubuntu 24.04, системные пакеты, импорты PyGObject и наличие `client/status_tray.py`. Он создаёт:

- `~/.config/autostart/status-light.desktop` — XDG-autostart для текущего пользователя;
- `~/.config/esp32-status-light/settings.env` — локальные настройки, если файла ещё не было.

Если задан `XDG_CONFIG_HOME`, оба пути создаются относительно него. Настройки находятся вне Git и не перезаписываются при повторной установке.

В `Exec` записывается фактический абсолютный путь к текущему checkout, поэтому запуск не зависит от текущего рабочего каталога. После перемещения или переименования репозитория повторите установку. Постоянно открытый терминал не нужен: приложение запускается графической сессией с `Terminal=false`.

Для проверки автозапуска завершите графический сеанс и войдите снова. Повторный запуск установщика обновляет только autostart-файл и не запускает второй экземпляр tray-клиента немедленно.

## Настройка host, port и timeout

По умолчанию используются:

- host: `status-light.local`;
- port: `80`;
- timeout: `3` секунды.

Отредактируйте `~/.config/esp32-status-light/settings.env`:

```sh
ESP32_STATUS_HOST="status-light.local"
ESP32_STATUS_PORT="80"
ESP32_STATUS_TIMEOUT="3"
```

Вместо mDNS-имени можно указать IPv4-адрес, например `192.168.1.50`. Этот файл читает установочный скрипт: после его изменения выполните `bash client/install_ubuntu.sh` повторно, чтобы обновить аргументы автозапуска.

Для ручного запуска из корня репозитория:

```sh
python3 client/status_tray.py
python3 client/status_tray.py --host 192.168.1.50 --port 80 --timeout 3
```

Host также можно задать переменной окружения:

```sh
ESP32_STATUS_HOST=192.168.1.50 python3 client/status_tray.py --port 80 --timeout 3
```

Явный `--host` имеет приоритет над `ESP32_STATUS_HOST`; без них используется `status-light.local`.

## Режимы и поведение без связи

В меню доступны три режима:

- `free` — свободен, зелёный светодиод;
- `busy` — занят, синий светодиод;
- `call` — в звонке, красный светодиод.

При недоступном ESP32 клиент показывает offline или ошибку запроса, но выбор режима не отменяется. Желаемый режим получает отметку pending («ожидает»), сохраняется в `~/.config/esp32-status-light/tray.json` (или под `XDG_CONFIG_HOME`), а его POST ставится в очередь. При refresh каждые 5 секунд клиент повторяет отправку до успешного ответа, поэтому после восстановления связи выбранный режим применяется без повторного выбора и перезапуска; сохранённый режим также отправляется при следующем запуске клиента.

Желаемый и подтверждённый режимы различаются: «ожидает» обозначает выбранный пользователем режим, который ещё не применён, а «на устройстве» — режим из последнего успешного ответа ESP32. До успешного POST выбранный режим нельзя считать подтверждённым устройством.

Проверьте, что компьютер и ESP32 находятся в одной локальной сети. ESP32 подключается только к сети 2,4 ГГц. HTTP API устройства доступен на `GET /health`, `GET /status` и `POST /status`.

## Журналы

Установщик не создаёт отдельный файл журнала и не настраивает systemd-службу. Сообщения автозапущенного приложения могут попасть в пользовательский журнал графического сеанса:

```sh
journalctl --user -b --no-pager | grep -iE 'status_tray|esp32|appindicator'
```

Наличие таких сообщений зависит от окружения рабочего стола. Если записей нет или нужна полная ошибка Python, завершите текущий экземпляр и запустите клиент вручную в терминале:

```sh
/usr/bin/python3 /полный/путь/к/репозиторию/client/status_tray.py --host status-light.local --port 80 --timeout 3
```

## Диагностика

### Нет значка в системном лотке

Сначала проверьте импорт `AyatanaAppIndicator3` командой из раздела «Зависимости». Ошибка `Namespace ... not available` обычно означает, что не установлен `gir1.2-ayatanaappindicator3-0.1` либо приложение запущено не системным Python.

В Ubuntu с GNOME также нужен работающий AppIndicator/StatusNotifier extension. Проверьте стандартное расширение Ubuntu:

```sh
gnome-extensions info ubuntu-appindicators@ubuntu.com
```

Если расширение отсутствует, установите системный пакет, включите расширение и повторно войдите в сеанс:

```sh
sudo apt install gnome-shell-extension-appindicator
gnome-extensions enable ubuntu-appindicators@ubuntu.com
```

В других окружениях рабочего стола проверьте, что включён системный лоток с поддержкой StatusNotifier/AppIndicator. Ошибки импорта и отсутствие значка — разные проблемы: успешный импорт не гарантирует наличие области для отображения индикатора.

### Автозапуск не срабатывает

Проверьте наличие и содержимое файла:

```sh
test -f ~/.config/autostart/status-light.desktop
```

В строке `Exec` должен быть существующий абсолютный путь к `client/status_tray.py`. Повторно выполните установщик от того же пользователя и проверьте ручной запуск с теми же аргументами. Не запускайте установщик через `sudo`: иначе он откажется создавать autostart для root.

### Не разрешается `status-light.local`

Проверьте mDNS и HTTP:

```sh
getent hosts status-light.local
curl --max-time 3 http://status-light.local/health
```

Ожидаемый ответ `/health` содержит `{"ok":true,...}`. Если IP-адрес работает, а имя `.local` — нет, проверьте mDNS-службы Ubuntu (`avahi-daemon`, `libnss-mdns`) или временно укажите IP-адрес в настройках. Если не отвечает и IP-адрес, проверьте питание ESP32, Wi-Fi 2,4 ГГц, локальную сеть и фильтрацию трафика.

## Удаление автозапуска

Выполните от того же пользователя:

```sh
bash client/uninstall_ubuntu.sh
```

Удаляется только `~/.config/autostart/status-light.desktop` (или соответствующий файл под `XDG_CONFIG_HOME`). Настройки `settings.env`, репозиторий и другие файлы пользователя сохраняются. Уже запущенный процесс деинсталлятор не останавливает: завершите его через меню tray-клиента или выйдите из графического сеанса.
